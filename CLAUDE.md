# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Build & Run Commands

```bash
flutter run -d edge            # Run web (primary target; -d chrome where Chrome is installed)
flutter run -d android          # Run on Android device/emulator
flutter test                    # Run all tests
flutter test test/health_calculator_test.dart   # Run a single test file
flutter analyze                 # Lint (uses flutter_lints)
firebase deploy --only hosting  # Deploy both hosting targets (run tools/build_hosting.ps1 first)
firebase deploy --only hosting:app  # Deploy just the app site
firebase deploy --only firestore:rules  # Deploy Firestore security rules
```

Release builds are signed with the upload key named in `android/key.properties` (gitignored, outside the repo: `C:/Users/brpet/keys/yumsum-upload.jks`, alias `upload`); without that file they fall back to the debug key, which Play rejects. The VS Code configs (`.vscode/launch.json`) add `--web-port 5000` for Edge (see App Check) and `--dart-define-from-file=config/off_account.json` for Android (see Open Food Facts). `tools/build_hosting.ps1` builds the web app into `build/hosting` (an `/app` build plus a `/webkit` build for Safari/iOS, behind a small redirect page) and copies the legal pages there. Firebase Hosting serves it with SPA rewrites at `yumsum.web.app` (hosting target `app`); the project's default site `lean-streak-project.web.app` (target `old`, public folder `tools/hosting-redirect`) 301-redirects every path to the same path there. The targets are mapped in `.firebaserc`.

## Architecture

**State management:** Riverpod 2. StreamProviders for real-time Firestore data, FutureProviders for one-off reads (recent meals, History's summaries and reviews), `AsyncNotifier` controllers in `lib/providers/` (`LogMealController`, `WeightLogController`, …) for mutations, and `Notifier`s for device settings (`ThemeController`, `ReminderSettingsNotifier`) and `launchActionProvider`.

**Routing:** GoRouter (`goRouterProvider`) with reactive auth-based redirects. The router listens to both `authStateProvider` and `userProfileProvider` and enforces: Splash → Auth → Onboarding → Dashboard (a profile that fails to load goes to `ProfileLoadErrorScreen`). Route paths live in `AppRoutes` in `lib/app/router.dart`.

**Screens:** Today (`DashboardScreen`) is home: calories/protein, the day's meals, a month graph and weight, with the quick-log bar (`QuickLogBar`, `lib/screens/dashboard/helpers/quick_log_bar.dart`) pinned at the bottom (type the meal, with the calories and protein as plain numbers in the two boxes that appear under it once the bar is in use, tap the mic, or tap the camera icon in the box to photograph the plate or a packet's barcode; while a box is focused and there are no calories yet, meals are offered as chips: with the name empty, up to five usually logged around this time of day (`usualMealsAt`: at least twice within 90 minutes of now, not already logged today); once typing, up to three of the last 50 distinct meal names that match (`distinctRecentMeals`), after a packaged-food search chip when not on the web). Editing a meal, or adding one to a past day, uses the meal form `showLogMealSheet` (`lib/screens/meals/log_meal_sheet.dart`), which has its own AI estimate. There are no bottom tabs; the top-left menu (`AppDrawer` in `lib/widgets/app_frame.dart`, on every page) lists Today, History, Weight & Progress, Plan Settings, Notifications and Account Settings. Today is the root and the other pages sit one level above it: picking a page from inside another swaps it (`pushReplacement`), so Back always returns to Today. History (`ReviewScreen`, route `/review`) combines a week/month calendar with the period review; tapping a day opens `showDayMealsSheet` (`lib/screens/review/day_meals_sheet.dart`) for adding, editing or deleting its meals. Plan Settings is `PlanSettingsScreen` in `lib/screens/profile/profile_screen.dart`; Account Settings is `AccountSettingsScreen` on route `/profile`.

**Styling:** Warm light and dark palettes (`AppPalette.light` / `AppPalette.dark` in `lib/core/constants/app_colors.dart`; `test/app_colors_contrast_test.dart` checks their WCAG contrast). `AppColors` is a set of static getters switched by `AppColors.isDark`, which `LeanStreakApp` sets from the stored ThemeMode (System/Light/Dark in the menu, `themeControllerProvider`) and the platform brightness, so expressions using `AppColors` cannot be `const`. `AppTheme.light`/`dark` are built from the palettes; use `AppCard` (`lib/widgets/app_card.dart`) for cards rather than hand-built containers. On wide browser windows `appShellBuilder` (`lib/app/app.dart`) shows the app as one centred column. The look follows the YumSum icon: cream backgrounds, the icon's orange (`primary`) for actions (buttons, links, focus, the mic) and its arc green (`veryGood`) for on track and for progress (Today's calorie and protein bars, the month bars, the weight chart), with amber for close and a raspberry red for off track and errors. Body text is Nunito and headings, app bar titles and big numbers are Fredoka (no Cyrillic, so it falls back to Nunito), both bundled in `assets/fonts` with their OFL licences registered in `main()`. Shapes are round and roomy: pill buttons and chips, 28px cards floating on a warm shadow (`AppCard`), round calendar days, `PillToggle` for two- and three-way switches, `IconBubble` behind icons, and `BowlNote` (the smiling bowl) for empty states. `AppLogoMark` shows `assets/logo.png` on the icon's gradient tile on phones; the web paints a drawn version (`_BowlPainter`), which stays sharp at small sizes. App icons for every platform are generated from `design/` by `python -I tools/make_icons.py`.

**Data flow:** Repository pattern. Each Firestore collection has a repository (`lib/repositories/`) that handles reads/writes; `AccountRepository` does the bulk deletes. Services (`lib/services/`) compose repositories for business logic; `FoodLookupService` and `FoodContributionService` talk to Open Food Facts over `http` instead, and `FeedbackRepository` to Formspree. Providers (`lib/providers/`) expose state to the UI and wire up controllers.

**Device settings:** SharedPreferences through `sharedPreferencesProvider` (`lib/providers/preferences_provider.dart`), overridden in `main()` so readers never wait on it (unoverridden it throws, so tests must override it). Keys: `theme_mode`, `reminders.*` (switches, times, `creatine_offered`), `off.app_uuid`, `contributions.count` and `feedback.sent_day`/`feedback.sent_count` (3 feedback messages a day).

**Firestore structure:** The profile is the `/users/{uid}` document; everything else is in subcollections under it: `meals`, `daily_summaries` and `weight_entries` (both keyed by date), `ai_usage/{yyyy-MM-dd}`, `day_edits/{yyyy-MM}` and `days_off/{yyyy-MM-dd}`. Period reviews are computed, not stored; legacy `check_ins` and `check_in_prompt_status` documents are only deleted along with the account. Reset progress on Weight & Progress clears `weight_entries` only; Account Settings' reset all data (`AccountRepository.resetAllData`) clears meals, summaries, weigh-ins and days off but keeps the profile and the AI and past-day edit counters, which `firestore.rules` only lets go up by one and delete after the profile is gone (account deletion deletes the profile first). The rules also allow only the known subcollections, with typed, size-capped fields: a new model field must be added to the rules too. Both that and account deletion re-authenticate with the account's email password (`AccountController`). Security rules (`firestore.rules`) enforce owner-only access.

## Key Domain Logic

- **Health calculations** (`lib/helpers/health_calculator.dart`): Pure static functions on `HealthCalculator` for BMI, BMR (Mifflin-St Jeor), TDEE, daily calorie targets (with per-gender calorie floors) and the protein target (grams per kg of goal weight, by training frequency). Extensively tested. Logging a weight (`WeightLogService`) recalculates the plan from it. Stored plans are recalculated at startup by `activityScaleMigrationProvider` when a profile's `planCalculationVersion` or `activityScaleVersion` is behind the constants in `lib/models/user_profile.dart`, so bump those when the formulas change.
- **Daily summaries** (`lib/services/daily_summary_service.dart`): `recomputeForDate` rebuilds a day from its meals whenever one is logged, edited or deleted (and on a day-off toggle or weigh-in), and deletes the summary when the day has no meals. Includes calorie and protein totals, meal count, and a green/yellow/red status based on adherence to target (±10% green, ±20% yellow, else red).
- **AI calorie estimation** (`lib/services/calorie_estimate_service.dart`): Uses Gemini 3.5 Flash-Lite. Every estimate prompt (`estimate`, `parseVoiceAudio`, `estimateFromPhoto`, `estimateProtein`; not `readLabel`) opens with `nutritionContext`, built from the profile's `country` and `usualFood` (asked in onboarding, editable in Plan Settings; profiles from before these fields default to the UK and Bulgarian home cooking), which also keeps meal and item names in the language the user wrote. Estimates return calories, protein and a per-item breakdown with each item's grams (`EstimateItem`); `EstimateBreakdown` shows it as one muted line that expands on tap, and correcting an item's grams rescales it (`resized`, `totalOf`) with no further AI call. `estimateFromPhoto` sends a resized JPEG with the same itemised prompt.
- **AI allowance and errors:** Typed, voice and photo estimates (and a contribution's `readLabel`) share a daily limit (`AiUsageRepository.dailyLimit`, 10/user/day) counted in Firestore; the automatic protein estimate for a named meal saved without protein (`LogMealController`) doesn't count. The counter is client-side and not tamper-proof; App Check, the per-user rate limit and the spend cap are the real protection. The bar shows how many are left once half are used, and the mic says so before recording once none are. Each call's token counts are printed to the debug log ("AI tokens: …"). `aiErrorMessage` maps server errors by their wording: not enabled → `aiNotSwitchedOnMessage`, 402/billing → `aiPausedMessage`, quota/429 → `aiBusyMessage` (not retried: the paid tier's limits are per minute); 5xx and connection errors get up to 3 attempts.
- **Period reviews** (`lib/services/period_review_service.dart`): Aggregates daily summaries into weekly/monthly review data, shown under the History calendar for finished days.
- **Past-day changes** (`lib/providers/log_meal_controller.dart`): adding, editing or deleting a meal on an earlier day uses one of 10 changes per calendar month (`DayEditRepository.monthlyLimit`); once they are used up the controller fails with `EditLimitExceededException`.
- **Today isn't judged mid-day:** a day only shows its green/yellow/red status once it is finished, on track, or over target (`hasSettledStatus` in `lib/widgets/day_status.dart`).
- **Day off:** the umbrella at the top right of Today takes today off (`confirmDayOff` explains it first; tap again to go back on plan; `DailySummaryService.setDayOff`). It is stored in `users/{uid}/days_off/{date}` (`DayOffRepository`), because the daily summary is rewritten on every meal change and deleted when a day has no meals; `recomputeForDate` copies it into `DailySummary.dayOff`. A day off never shows a status (`hasSettledStatus` is false), and period reviews count its calories but leave it out of the on-track/close/off-track tally, the consistency rate and best/worst day, reporting it as a days-off count instead.

## Models

All stored models use manual Firestore serialization (no codegen). Each has `fromFirestore` / `toFirestore` methods. Enums use `fromString` factory constructors, some with legacy value handling (`ActivityLevel` and `TrainingFrequency` accept old string formats; a profile without `trainingFrequency` gets `TrainingFrequency.legacyDefaultFor`).

Key models: `UserProfile` (with enums for Gender, ActivityLevel, TrainingFrequency, WeightLossPace, GoalPaceLevel), `Meal` (optional name, calories, optional protein; legacy `tags`/`note` fields are ignored), `DailySummary` (with optional protein and `dayOff`), `WeightEntry` (one per day, with a `WeightSource`), and `PeriodReview` (computed only, never stored).

## Conventions

- Dart SDK `^3.11.4`, uses modern Dart 3 features (switch expressions, pattern matching, records).
- Copy: short and plain. British English, "you", sentence case for buttons and messages (page names like Plan Settings stay as titled), no "Please", no exclamation marks except the contribution "Thank you!". Errors say what failed and what to do next ("Could not X. Try again.", or "Could not load X." for a page). Plain words over jargon ("adjusts", not "recalculates"). The Day off dialog lists its effects as one-line icon rows; keep them and the button labels short enough for a 360dp phone.
- Voice logging records a short clip with `record` (16 kHz mono PCM, wrapped as WAV by `lib/helpers/wav.dart`) and sends the audio to Gemini (`parseVoiceAudio`), which understands English, Bulgarian or a mix with no language setting. Recording ends on the Stop button, after a pause once something was said, or at 30 s.
- AI calls go through Firebase AI Logic (`firebase_ai`, Gemini Developer API backend, `FirebaseAI.googleAI()`), so there is no API key in the app; the Firebase project must have AI Logic enabled (console → Build → AI Logic). The project is on the Blaze plan with the Gemini API's paid tier (since 24 October 2026, required for UK/EU users): $5 prepaid in AI Studio with auto-reload off, a £3/month spend cap on "Gemini Developer API (AI Logic)", and the per-user limit lowered to 10 requests a minute (see `docs/plans/03-ai-costs-and-earning.md`).
- Every AI call carries a Firebase App Check token (`lib/core/config/app_check.dart`, activated in `main()`): debug builds use the debug provider, whose token (printed in the log at startup) must be registered under App Check → Apps → Manage debug tokens; release builds use Play Integrity on Android and DeviceCheck on iOS, and the web uses reCAPTCHA Enterprise (Fraud Defense in Google Cloud; classic v3 can no longer be registered) with the public site key in `recaptchaSiteKey`. `web/index.html` turns on the debug token on localhost; run the web app on a fixed port, as the VS Code "YumSum (Edge)" config does with `--web-port 5000`, because the token is stored per origin in the browser profile Flutter keeps under `.dart_tool/chrome-device`, and register it under the `lean_streak (web)` app's debug tokens. Firebase makes App Check enforcement mandatory for AI Logic from 2 November 2026.
- Packaged foods: on phones the bar's one camera button opens `MealCameraPage` (`camera` plugin, 720p): every preview frame (NV21 on Android, BGRA on iOS) goes to ML Kit's on-device barcode reader (`google_mlkit_barcode_scanning`, retail formats only), and the first barcode closes the page by itself; the shutter instead takes a photo for the AI. The page lets the camera go when the app is backgrounded and picks it up on return. Elsewhere `openMealCamera` (`lib/screens/dashboard/helpers/meal_photo.dart`) falls back to a file picker. A barcode goes to `FoodLookupService.byBarcode` (Open Food Facts `/api/v2/product/{code}.json`, only the barcode is sent, `app_name`/User-Agent identify the app); one the database doesn't know is reported with a nudge to photograph the packet, and the camera ignores that barcode next time so it can. ML Kit needs iOS 15.5 or later, so an iOS build has to raise the deployment target (still 13.0). The search chip (typed name, no calories, 3+ characters, not on the web because `search.openfoodfacts.org` sends no CORS header) opens `showFoodSearchSheet` (`FoodLookupService.search`, the profile's country first). Either way `showPortionSheet` asks for the grams (prefilled from `serving_size`, else `quantity`, else 100); its Done button fills the boxes with label figures, and the meal is saved from the bar. No AI call, no daily-limit use. `PackPhoto` (`lib/widgets/pack_photo.dart`) shows the front of the pack (`PackagedFood.imageUrl`, from `image_front_small_url`, which both the barcode and search requests ask for): 48px in the search results, 72px beside the name in the amount sheet, which leaves it out when there's no photo.
- Contributing to Open Food Facts: when Open Food Facts has never heard of a scanned barcode (`BarcodeLookup.listed` is false; a listed product without calories is not offered, since contributing would overwrite someone else's entry), `_offerContribution` in the quick-log bar shows `inviteToContribute`, then `takeProductPhotos` (`MealCameraPage` with `photoSteps`: the front, then the nutrition table), then `showContributeSheet`, which `readLabel` prefills (one Gemini call with both photos, counts towards the daily limit, told to copy the label and never guess) for the user to check. `FoodContributionService` posts the details to `cgi/product_jqm2.pl` (`product_name_<lc>` with `lc` from the language `readLabel` reads off the pack, else `productLanguage`; `add_brands`; `add_countries` and `cc` only for recognised UK/Bulgaria spellings; `nutriment_<id>` per 100 g, or per 100 ml for volume packs) and each photo to `cgi/product_image_upload.pl` (`front_<lc>`, `nutrition_<lc>`) under the app's shared Open Food Facts account, with a random per-install `app_uuid` (prefs `off.app_uuid`) so their moderators can block one contributor.
- The Open Food Facts account is given at build time with `--dart-define-from-file=config/off_account.json` (`OFF_USER_ID`, `OFF_PASSWORD`, `OFF_HOST`; gitignored, copy `config/off_account.example.json`; the VS Code Android config passes it). `OFF_HOST` defaults to `world.openfoodfacts.org`; `world.openfoodfacts.net` is their test server, with its own accounts and the shared basic-auth login off:off. Without an account (`FoodContributionService.isConfigured`), or on the web, contributing isn't offered and the bar just says the barcode is unknown. A thank-you screen counts contributions per device (prefs `contributions.count`), and from there the product can go straight to the portion sheet. The plan and set-up steps are in `docs/plans/01-contribute.md`.
- Crash reporting: `firebase_crashlytics` on Android/iOS only (it has no web build); the handlers are set in `main()` after Firebase is initialised. Account Settings' feedback tile opens `showFeedbackDialog` (`lib/widgets/feedback_dialog.dart`: a Problem/Idea/Other `PillToggle`, which sets the box's prompt and the email subject, over one message box), which `FeedbackRepository` posts as JSON to a Formspree form (`FeedbackRepository.endpoint`, set up in the help.yumsum Formspree account); Formspree emails it to `supportEmail` (help.yumsum@gmail.com, `lib/core/constants/app_info.dart`, also in the legal pages and the Open Food Facts User-Agent) with the user's email as reply-to. No Firestore, no extension. The free plan takes 50 messages a month. Onboarding and Plan Settings accept ages 18–120, matching the legal pages.
- Sign-in is email/password (sign-up sends a verification email and signs out; unverified sign-ins fail with `EmailNotVerifiedException`) or Google: Firebase's popup on the web, `google_sign_in` 7 on phones, which needs the web client ID that the google-services plugin reads from `google-services.json` (present once the Google provider is enabled in Firebase Auth); `googleSignIn()` in `auth_controller.dart` initialises the plugin once, as it requires. Backing out of the Google flow (`backedOutOfGoogle`) is not shown as an error. An account without a password login (`hasPasswordLogin` in `account_controller.dart`, i.e. Google only) confirms Reset all data and Delete account with Google instead of a password (`showPasswordConfirmDialog(askPassword: false)`), and Account Settings hides Change email and the password reset for it.
- Legal pages live in `tools/hosting/privacy.html` and `terms.html`; `build_hosting.ps1` copies them to the hosting root and `firebase.json` has `cleanUrls`, so they're served at `/privacy` and `/terms`. `LegalLinks` (`lib/core/constants/legal_links.dart`) holds the URLs, including the Open Food Facts credit its licence asks for. `LegalFooter` (sign-in; on the web it also carries the reCAPTCHA attribution line Google requires when the badge is hidden) and the legal section of Account Settings open them; `MedicalNote` is the health disclaimer shown under the plan preview in onboarding and Plan Settings. Both widgets are in `lib/widgets/legal_links.dart`.
- Android home-screen widget: `LogWidgetProvider.kt` (a `home_widget` `HomeWidgetProvider`) draws `res/layout/log_widget.xml` (a 2×1 mini log bar declared in `res/xml/log_widget_info.xml`, colours in `values(-night)/colors.xml`); taps open the app with `leanstreak://log/text` or `leanstreak://log/voice`, which `launchActionForUri` maps to `LaunchAction.typeLog`/`voiceLog`. Flutter deep linking is off in the manifest so go_router never sees those URIs, and `MainActivity` blanks the intent on a relaunch from Recents. The app-icon shortcut (`quick_actions`, id `log_voice`) uses the same path.
- `NotificationService` (`flutter_local_notifications`, Android/iOS only) schedules a daily meal reminder (20:30), a weekly weigh-in reminder (Saturday 20:00 by default; day and time are set under the switch) and a daily creatine reminder (off by default, 09:00); the switches live on the Notifications page (`NotificationsScreen`, in the menu) and `reminderSyncProvider` keeps the schedules in step (asking for permission once on first run). Today offers the creatine reminder once in a dialog (`offerCreatineReminder`) from the day after sign-up until the end of the first week (`shouldOfferCreatine`), and either way says where to find it. A tap on the weigh-in reminder becomes `LaunchAction.logWeight` (`lib/app/launch_actions.dart`, bound in `main()` before Firebase so a cold-start tap isn't lost), which Today consumes by opening the log-weight dialog; the shortcut and widget actions are consumed by the quick-log bar.
- The app targets web primarily but also supports Android and iOS. The Android application ID and iOS bundle ID are `com.bpetrov.yumsum` (Kotlin lives under `com/bpetrov/yumsum`); `android/app/google-services.json` belongs to that Firebase Android app.
- The app is called YumSum (renamed from LeanStreak in October 2026, after a name clash). Only what users or Open Food Facts see uses the new name; the Dart package `lean_streak`, class names such as `LeanStreakApp`, the `leanstreak://` launch URIs, debug log tags and the Firebase project `lean-streak-project` (and its `firebaseapp.com` auth domain) keep the old one; the website moved to `yumsum.web.app`.
- Tests never touch Firebase, the network or device hardware. Screens are pumped in a `ProviderScope` inside `MaterialApp(theme: AppTheme.light, …)`, overriding whatever reads Firestore or the device: `currentUidProvider`, `userProfileProvider`, the data providers, `sharedPreferencesProvider` (after `SharedPreferences.setMockInitialValues`), the AI and Open Food Facts service providers, `audioRecorderProvider`, `mealCameraProvider` and `productPhotosProvider` (`test/quick_log_bar_test.dart` has the full set). Controllers are faked by subclassing, services with `Fake implements …`, and the Open Food Facts services take an `http.Client` for `MockClient`. The quick-log boxes have keys (`quick-log-name`, `-kcal`, `-protein`).
- `docs/plans/` holds the owner's launch plans (01 contributing, 02 name/email/website, 03 AI costs and earning) with set-up steps and checklists. `README.md` and `leanstreak_agent_build_spec.md` are out of date (meal tags, check-ins, `speech_to_text`, Gemini 2.5); trust the code and this file over them.
